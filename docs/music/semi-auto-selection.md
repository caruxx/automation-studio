# SUNO生成・取得を自動化し、採用をハートで選ぶ

2026-09-29のユーザー指示で、同タイトル・同程度の尺の2テイクを人が聴き比べる方式へ変更した。短い方の自動採用は、SUNOの新規取得バッチでは使わない。

## 操作

1. Automation StudioのSUNO画面から生成する。SUNOのCustom durationは従来の指定を維持する。4分の制作では`duration_seconds: 240`を指定する。
2. 生成完了後、2テイクとも自動取得する。SUNO画面でハートを付ける必要はない。
3. SUNO画面の「楽曲を聴き比べてハートで採用」、または動画の楽曲タブから聴き比べ画面を開く。
4. 各タイトルから1テイクにハートを付ける。同タイトルのもう片方を選ぶと、以前のハートが解除される。ハートを外すと未選択へ戻る。
5. 全タイトルを選んだら「採用曲の後処理へ」。選ばれた曲だけを`music/`へ書き出す。取得した2テイクの原本は変更せず残す。
6. 動画の制作工程を再開する。CLIなら`python3 Python/app_pipeline.py <vol> --from rename`。生成からやり直してSUNOクレジットを二重消費しない。

取得不足・未選択・後処理前の状態では、rename / premiere / export / upload工程が停止する。pipelineの終了コード`79`は選択待ちを表す。自動再投入の対象にしない。SUNO queueも生成と取得が終わったジョブを`awaiting_selection`として扱い、選択待ちのまま再生成しない。

今回のセットは`output/suno-groove-ten-20260929`、レビューIDは`6d0696304171342cf6b3`。20テイク、10タイトル。過去の`selected/`は以前の機械的な候補選定結果で、新しい採用台帳ではハートを付けた曲が基準になる。

## 公開タイムスタンプの曲名

採用テイクの末尾に`(1)`や`（２）`が付いていても、タイムスタンプ・字幕では番号を表示しない。`Silver Avenue(1)`は`Silver Avenue`と表示する。テイク番号と原本名は採用台帳に保持し、`(Live)`など数字以外の括弧書きは保持する。既存タイムコードを概要欄へ取り込む経路も同じ処理を通す。

## タイトルを重複させない仕組み

正本は`~/.config/automation-studio/music_catalog.sqlite3`。チャンネル切替とは独立した永久台帳で、直近20件・40件の履歴制限に影響されない。`APP_MUSIC_CATALOG_DB`で保存場所を指定できる。DBファイルをGitに入れない。

- 既存チャンネルのMP3、生成バッチの取得ログ、従来のSUNO履歴を取り込む。今回の初回取り込みは900種類の正規化タイトル。
- Create前にタイトルを予約し、DBの一意制約とトランザクションで重複を防ぐ。LLM起草、`--songs-file`、共有SUNO送信入口のどれでも予約する。
- 大文字・小文字、全角、空白、句読点だけの違いも同一とみなす。
- 使用済みタイトルなら`Afterglow`などの補助語を付けて新しいタイトルにする。Styles・Exclude・歌詞はそのまま保つ。
- 1回の生成で出る2テイクは同じ予約を共有する。別の生成リクエストでは同じタイトルを使わない。
- 予約したタイトルをSUNOフォームに入力・読み戻しできなければ、Createを実行しない。送信に失敗しても予約は残し、受理状況が不明なリクエストの再利用を避ける。

取り込み対象はこのMacから見える登録チャンネル・ローカル素材・残っている生成ログ。ログにも素材にも残っていないSUNOライブラリの全履歴を網羅した、という意味ではない。別のPCで同時に生成する場合の全体一意性には、共通サーバーのDBによる予約が必要になる。Drive同期中のSQLiteを複数PCから同時操作する運用は前提にしない。

## Fable / Claude / Codex / その他ツール共通の契約

通常の制作では既存CLIとAPIを使う。モデル自身が尺やファイル名から採用を推測しない。

```text
SUNOは1タイトルにつき2テイクを生成・取得する。
採用はAutomation Studioの聴き比べ画面のハートで人が決める。
app_music_catalog.require_selection(folder)を確認してから後処理する。
app_music_catalog.require_selection(folder, processed=True)を確認してから動画化する。
未選択は終了コード79 / awaiting_selectionで停止し、生成は繰り返さない。
採用IDは.music_review.jsonのtakes[].clip_idとselectedを読む。
全テイクの原本を保持する。既存selected/や短い尺を理由に自動採用しない。
タイトルはCreate前にapp_music_catalog.prepare_submissionで予約する。
SUNOの入力原稿と4分設定はbeat-soul-recipe.mdとプリセットを基準にする。
```

各フォルダの`.music_review.json`に曲ID、元ファイル、ハート、選択revision、後処理revision、取得不足の状態を原子的に保存する。DBのeventsにはタイトル予約・送信・取得・ハート変更・後処理を時刻付きで残す。JSONは他ツールから読める持ち運び用の記録。DB未登録のフォルダを同じ原本・取得ログとともに登録すればハートを復元できるが、別PCへコピーしたときは音声を再度後処理して確認する。

API:

|操作|URL|
|---|---|
|セット一覧|`GET /api/music/reviews`|
|2テイク・採用状態|`GET /api/music/reviews/{id}`|
|試聴|`GET /api/music/reviews/{id}/audio/{clip_id}`|
|ハート|`POST /api/music/reviews/{id}/heart`、本文`{"clip_id":"...","selected":true}`|
|採用曲だけ後処理|`POST /api/music/reviews/{id}/process`|
|後処理状態・終了コード|`GET /api/process/status`|

動画の従来`tracks` / `track-like` APIも同じ採用台帳へ接続する。新方式ではハート操作で音声ファイルをリネームしない。既存の後処理済み動画は自動移行しない。

選び直したら、古い`music/`のまま動画に進ませない。後処理は一時フォルダで全採用曲を作ってから入れ替え、以前の出力は`.music_previous/`へ退避する。FFmpegの連結音声キャッシュにも音源のサイズ・更新時刻を含め、同じタイトルの別テイクへ切り替えた後の古い音声の再使用を防ぐ。未管理の既存`music/`は上書きせず停止する。

## 検証

`python3 -m unittest discover -s Python/tests -p 'test_music_review.py' -v`

別プロセスでのタイトル予約競合、同尺テイクの未選択停止、ハートの排他切替、原本保全、取得不足、後処理失敗時の旧出力保全、既存動画の非移行、API共通選択、動画工程の停止を検証する。実音声と実ブラウザの確認には制作素材を削除せず、専用のテスト素材を使う。

2026-09-29の確認では21項目のテストが成功。専用の実MP3をブラウザでハート選択・排他切替・再読込・後処理し、採用音源の周波数と原本4ファイルのSHA256を独立確認した。現在の20テイクの取得完了・試聴Range応答・10タイトル未選択の表示も実APIで確認済み。新しいSUNO送信引数はモックで4分・Exclude・自動取得の伝達を確認し、この変更検証のための追加生成は行っていない。Adobeの実書き出しとYouTube公開は今回の検証対象外。
